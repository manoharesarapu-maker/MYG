# Guide — Architecture

Guide is the citizen-facing conversational intake layer of a larger civic
intelligence platform. This document restates the non-negotiable principles
this codebase is built around, so anyone extending it (including a future
production build-out) understands what must never change.

## Six internal layers

1. **Ingestion** (`ingestion/`) — turns council policy source material into
   structured content. In production this parses real documents (e.g. via
   Unstructured.io) into the taxonomy schema. In this demo it is a stub that
   reads pre-authored YAML from `taxonomy/` and returns it through the same
   `ingestPolicyDocument(source): StructuredContent` interface a real
   pipeline would implement — so the pipeline can be swapped in later
   without touching any caller.
2. **Intent taxonomy** (`taxonomy/`) — the decision tree of citizen intents,
   branches, and requirements. This is curated, versioned data, not
   something inferred at runtime. It is the spine of the whole system.
3. **Classification** (`classifiers/`) — matches free-text citizen input to
   a taxonomy node. Uses Claude for semantic matching
   (`semantic-match.ts`), falls back to keyword matching
   (`rules-fallback.ts`) when confidence is low, and always returns a
   confidence score. A low-confidence result must produce a clarifying
   question, never a guess.
4. **Question generation** (`agents/question-*`) — decides what to ask next.
   The decision of *what* to ask is deterministic, driven by the matched
   branch's requirement list (`question-selection-rules.ts`). Only the
   *phrasing* of the question is generated by Claude
   (`question-generation-semantic.ts`).
5. **Extraction** (`agents/extraction-*`) — turns a citizen's free-text
   answer into a structured value using Claude
   (`extraction-semantic.ts`), then validates it deterministically against
   the requirement's expected type/format (`extraction-validation-rules.ts`).
   Invalid extractions trigger a re-ask, never a silent guess.
6. **Handoff** (`handoff/`) — once every requirement for a branch is
   captured, produces a structured, complete case object. This is what
   would be hand a real system off to Validator in production. In this demo
   it is rendered as a summary screen instead of being sent anywhere.

## Principles that must never be violated

- **LLMs sit at semantic edges only.** Claude is used to understand
  free text, phrase questions, and extract structured values. Claude is
  never used to decide eligibility or outcomes — that logic lives in plain
  deterministic code (`decision_logic` implemented in `agents/` and
  `governance/`), driven entirely by taxonomy data.
- **Curated content is the only citizen-facing source of truth.** Every
  fact stated to a citizen must trace back to a taxonomy/content entry.
  Every semantic system prompt explicitly instructs Claude not to invent
  policy details, fees, eligibility rules, or timeframes.
- **Tier 0 governance is structural, not policy.** Anything touching
  welfare, hardship, or safeguarding is detected and escalated by explicit
  code in `governance/tier0-rules.ts`, never left to model judgement. Tier 0
  interactions are excluded from "resolved" or "commercial" counting logic.
- **No agent framework.** The conversation flow is a hand-written,
  explicit, inspectable state machine (`agents/conversation-state-machine.ts`).
  No LangChain, AutoGPT, CrewAI, or similar.
- **Telemetry is schema-first.** Every state transition emits a typed event
  defined in `telemetry/schema.ts`, so behaviour is auditable end to end.

## Data flow per conversational turn

```
citizen input
  -> classifiers/semantic-match.ts (+ rules-fallback.ts)
  -> governance/tier0-rules.ts        (checked on every turn, can short-circuit)
  -> agents/conversation-state-machine.ts
       -> agents/question-selection-rules.ts   (what to ask)
       -> agents/question-generation-semantic.ts (how to phrase it)
       -> agents/extraction-semantic.ts + extraction-validation-rules.ts (parse the answer)
  -> handoff/buildCaseObject.ts        (once branch is complete)
  -> telemetry/schema.ts               (event emitted at every step above)
```

All of this is orchestrated per-turn by
`services/guide-orchestrator/handler.ts`, called from
`app/api/guide/route.ts`.

## Why this matters

The file structure, naming, and layering here are deliberately
production-shaped. The data layer (taxonomy content, session storage) is
hardcoded/mocked for this demo, but every interface is written so that real
infrastructure — a document ingestion pipeline, a Postgres + pgvector
store, a real session store — can be dropped in behind these same
interfaces without restructuring the codebase.
